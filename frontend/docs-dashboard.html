Visión del Producto y Principios Rectores

Rama Activa: feature/api-equivalencias (2dc2dab)

AppCalorias es una aplicación web colaborativa y asimétrica pensada para resolver la brecha entre el criterio clínico del nutricionista/entrenador (Coach) y la simplicidad operativa del usuario de gimnasio (Alumno).

👤 Alumno: "Acciones, no datos"

  • Delega la complejidad de fórmulas metabólicas en su coach o plantillas inteligentes.
  • Registra comidas en menos de 10 segundos con el botón 1-Tap Check ("Lo comí").
  • Reemplaza alimentos sobre la marcha sin quebrar la distribución de macronutrientes gracias al Algoritmo L1.
  • Monitorea su hidratación y suplementación con alertas de seguridad y recordatorios táctiles.

🏋️ Coach: "El método le pertenece"

  • Modela el contexto energético del alumno calculando BMR (Mifflin-St Jeor), NEAT y TDEE.
  • Estructura planes alimenticios en 4 comidas diarias con alimentos fijados por cantidad/porción.
  • Supervisa el cumplimiento diario en tiempo real mediante la vista agregada coach_alumno_summary.
  • Genera vínculos seguros e instantáneos mediante códigos aleatorios de cliente (client_code).

Procedimientos Almacenados Críticos (RPC PostgreSQL)

supabase/migrations/20261016_vincular_alumno_rpc.sql 
CREATE OR REPLACE FUNCTION public.vincular_alumno_por_codigo(p_codigo TEXT)
RETURNS JSONB
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  v_coach_id UUID := auth.uid();
  v_alumno_id UUID;
  v_perfil_alumno RECORD;
BEGIN
  IF v_coach_id IS NULL THEN
    RETURN jsonb_build_object('ok', false, 'error', 'No autenticado');
  END IF;

  SELECT id, nombre, usuario INTO v_perfil_alumno
  FROM public.perfiles
  WHERE UPPER(client_code) = UPPER(TRIM(p_codigo)) AND rol = 'alumno';

  IF NOT FOUND THEN
    RETURN jsonb_build_object('ok', false, 'error', 'Código de alumno inexistente');
  END IF;

  v_alumno_id := v_perfil_alumno.id;

  INSERT INTO public.alumnos_coach (coach_id, alumno_id, vinculado_en)
  VALUES (v_coach_id, v_alumno_id, NOW())
  ON CONFLICT (coach_id, alumno_id) DO NOTHING;

  RETURN jsonb_build_object('ok', true, 'alumno_id', v_alumno_id, 'nombre', v_perfil_alumno.nombre);
END;
$$;

Algoritmo de Equivalencias: Mediana Ponderada en Distancia L1

Resolución Analítica en O(1)

El motor de reemplazo nutricional de AppCalorias resuelve analíticamente la porción óptima \(x^*\) (en gramos) de un alimento alternativo \(B\) para sustituir un alimento planificado \(A\).

Función Objetivo de Minimización:

E(x) = w_1 · |C_A - x·C_B|/C_A + w_2 · 4|P_A - x·P_B|/C_A + w_3 · 4|CH_A - x·CH_B|/C_A + w_4 · 9|G_A - x·G_B|/C_A

Donde \(w_1 = 0.20\) (peso calórico global) y \(w_2, w_3, w_4\) se distribuyen proporcionalmente al 80% restante según la densidad de macronutrientes del alimento original. La solución \(x^*\) es la mediana ponderada de los 4 multiplicadores individuales.

25 Preguntas Estratégicas para Devs & Tech Leads

Mostrando 25 de 25

Cuestionario técnico exhaustivo con propuestas de arquitectura y trade-offs para resolver antes del lanzamiento a producción. Utilizá los filtros cruzados por Eje temático y por Nivel de Prioridad:

Eje Temático:
Prioridad:
1. Estrategia sin Bundler a Escala (Cache-Busting de ES Modules) Eje A · P1
Problema Técnico: Al importar módulos directamente mediante ESM CDN, los navegadores de clientes recurrentes pueden retener archivos cacheados tras una actualización de código.
Propuesta Arquitectónica: Adoptar querystrings con versión fija ?v=1.2.0 en los imports de cada script HTML durante despliegues automatizados de Git.
2. Sincronización Offline-First en el Gimnasio (Background Sync) Eje A · P0
Problema Técnico: Muchos gimnasios tienen sótanos con nula señal móvil; si el alumno toca "Lo comí", la petición a Supabase falla.
Propuesta Arquitectónica: Implementar capa de persistencia en IndexedDB con Service Worker y sincronización diferida al recuperar conexión.
3. Manejo Centralizado de Estado Reactivo entre Pantallas Eje A · P2
Problema Técnico: Cada UI mantiene variables globales en memoria (`let elegido`, `let clientes`). Si cambia la fecha, no siempre se refrescan los componentes hijos.
Propuesta Arquitectónica: Crear un bus nativo con CustomEvent y BroadcastChannel para sincronizar pestañas en segundo plano.
4. Sanitización y Validación en Formularios Críticos (crear-alimento.html) Eje A · P0
Problema Técnico: La inserción directa de nombres y notas de alimentos puede permitir ataques XSS o inyecciones si no se escapan en el DOM al renderizar listas.
Propuesta Arquitectónica: Sanitización estricta mediante textContent y esquemas de validación tipo Zod/JSON Schema en el cliente antes de llamar a PostgREST.
5. Componentización de SVG Sprites vs Inyección Inline Eje A · P2
Problema Técnico: Múltiples vistas replican SVGs idénticos (íconos de chevron, fuego, manzana, pesa), inflando el peso del HTML innecesariamente.
Propuesta Arquitectónica: Unificar en un sprite central frontend/assets/icons.svg consumido mediante <svg><use href="assets/icons.svg#id"/></svg>.
6. Desacoplamiento Formal de Antropometría en PostgreSQL Eje B · P0
Problema Técnico: La tabla antropometrias aún existe en migraciones previas a pesar de que la UI ya la descartó.
Propuesta Arquitectónica: Ejecutar migración 20261017_drop_antropometria.sql y redefinir permisos de coach sin exponer columnas obsoletas.
7. Normalización Relacional vs JSONB en Planes de Alimentación Eje B · P1
Problema Técnico: Almacenar las 4 comidas como un blob JSONB en planes_alimentacion dificulta auditorías y consultas de adherencia.
Propuesta Arquitectónica: Normalizar a tablas relacionales plan_meals y plan_items con claves foráneas para auditoría de reemplazos e integridad referencial.
8. Performance de la Vista SQL coach_alumno_summary Eje B · P1
Problema Técnico: Calcular agregados semanales para coaches con cientos de alumnos provocará consultas secuenciales lentas.
Propuesta Arquitectónica: Convertir la vista en una MATERIALIZED VIEW refrescada periódicamente mediante la extensión pg_cron de Supabase.
9. Manejo de Zonas Horarias y Registros a Medianoche Eje B · P1
Problema Técnico: Si un alumno cena a las 23:45 y registra a las 00:15 UTC, el registro se asigna al día siguiente erróneamente.
Propuesta Arquitectónica: Almacenar la columna log_date como tipo DATE estricto en la zona horaria del cliente (ej. America/Argentina/Cordoba), desacoplada del created_at TIMESTAMPTZ.
10. Riesgo de Colisión en Generación de Código client_code Eje B · P1
Problema Técnico: La función generar_codigo_cliente() utiliza un bucle con números aleatorios en formato NF-1234-AB.
Propuesta Arquitectónica: Añadir índice único y un límite de 5 reintentos con backoff exponencial para garantizar inserción en menos de 5 ms sin deadlocks.
11. Fuente de Datos Definitiva del Catálogo de Alimentos Eje C · P0
Problema Técnico: Actualmente solo existen ejemplos aislados en maquetas.
Propuesta Arquitectónica: Base curada en Supabase (500 alimentos frecuentes de consumo regional) combinada con la API de Open Food Facts para escaneo de códigos de barra.
12. Soporte para Unidades y Medidas Caseras (1 Banana, 2 Huevos) Eje C · P1
Problema Técnico: El algoritmo L1 opera exclusivamente en gramos, pero el usuario casual no pesa una fruta ni un huevo.
Propuesta Arquitectónica: Almacenar el gramaje por unidad promedio (ej. 1 huevo M = 55g, 1 banana = 120g) y redondear al múltiplo de unidad más cercano.
13. Calibración y Validación Clínica de Umbrales L1 Eje C · P1
Problema Técnico: Los umbrales de equivalencia óptima (≥90% adherencia, ≥75% similitud) requieren validación nutricional.
Propuesta Arquitectónica: Panel de calibración donde el nutricionista jefe valide la matriz de penalización por micronutrientes y fibra dietaria.
14. Restricción por Categorías y Perfiles Lipídicos Eje C · P0
Problema Técnico: Evitar que el algoritmo matemático sugiera reemplazar hidratos complejos (arroz) por grasas puras (manteca) si solo coinciden calorías.
Propuesta Arquitectónica: Matriz de compatibilidad biológica obligatoria antes de ejecutar la minimización L1, bloqueando cruces incompatibles.
15. Alimentos Creados por Usuarios: Privacidad vs Catálogo Comunitario Eje C · P2
Problema Técnico: Cuando un alumno o coach crea un alimento custom en crear-alimento.html, este puede contener errores o duplicar ítems existentes.
Propuesta Arquitectónica: Visibilidad privada por defecto (is_public = false), con un flujo de moderación técnica para promover alimentos de calidad al catálogo global.
16. Protección contra Registro Abierto y Abuso de Cuentas de Coach Eje D · P1
Problema Técnico: En registro.html cualquier persona puede seleccionarse como coach sin verificación profesional.
Propuesta Arquitectónica: Implementar tabla de códigos de invitación o revisión manual de estado approved = false antes de habilitar clientes.
17. Rate-Limiting en RPC Pública usuario_disponible Eje D · P1
Problema Técnico: Scraping masivo para enumerar nombres de usuario existentes en el sistema.
Propuesta Arquitectónica: Configurar rate limiting por IP mediante Supabase Edge Functions o Cloudflare Turnstile en el registro.
18. Ciclo de Vida de Tokens JWT y Prevención de Pérdida de Datos Eje D · P0
Problema Técnico: Si el token expira mientras el usuario completa un formulario extenso de comidas, la petición POST falla con error 401.
Propuesta Arquitectónica: Listener global con supabase.auth.onAuthStateChange que renueve proactivamente la sesión y reintente peticiones encoladas.
19. Privacidad y Borrado de Datos (GDPR / Desvinculación de Coach) Eje D · P1
Problema Técnico: Qué ocurre con los registros históricos del alumno cuando este desvincula a su coach.
Propuesta Arquitectónica: Desvinculación lógica (unlinked_at), revocando acceso al coach de manera instantánea mediante RLS sin eliminar el historial médico del alumno.
20. Validación de Roles en el Servidor (Bypass de Frontend) Eje D · P0
Problema Técnico: Si un alumno manipula localStorage o invoca directamente endpoints de Supabase con role=coach.
